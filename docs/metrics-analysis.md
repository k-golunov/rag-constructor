# Основа интерфейса «Анализ метрик»

Раздел находится во вкладке проекта **«Анализ метрик»** и использует готовую
пакетную очередь Celery. Ранее эта вкладка называлась «Пакетные запуски».
Расчёт метрик пока не подключён: интерфейс собирает исходные данные и показывает
статусы обработки. Оценки качества, рейтинги и итоговые баллы не рассчитываются.
Оценки поиска у найденных фрагментов — исходные значения Qdrant, а не метрики качества ответа.

## Сценарий без кода

1. Во вкладке «Наборы вопросов» создайте или импортируйте вопросы, добавьте необязательные
   эталоны/подтверждения и проверьте примеры человеком.
2. В «Анализе метрик» выберите набор, неизменяемую версию и раздел tuning/test.
3. Добавьте варианты. Для каждого можно использовать текущие настройки проекта либо
   сохранённую конфигурацию предыдущего пакетного запуска и при необходимости изменить
   отдельные действующие параметры. Пустые поля наследуются из выбранной базы.
4. Нажмите «Проверить настройки и индексы». Появятся таблица различий, количество вопросов
   и результатов, необходимость построения индексов и указание общего индекса для вариантов.
5. Нажмите «Начать сбор ответов» либо сохраните подготовленный запуск без выполнения.
   Сбор идёт в фоне; страницу можно закрыть и позже вернуться к сохранённому запуску.
6. В результатах доступны прогресс, ошибки, отмена/продолжение, повтор после ошибки и
   независимый повторный прогон. Фильтры работают на сервере, а не только на загруженной странице.
7. Для каждого результата рядом показаны **ответ модели / фактически переданный контекст /
   эталон из зафиксированной версии набора**. Отдельно видны отсутствие ответа в документах,
   подтверждающие выдержки и их позиции, найденные фрагменты и оценки поиска.
8. Кнопки «Экспорт JSON» и «Экспорт CSV» выгружают весь запуск со всеми попытками,
   независимо от текущего фильтра и количества загруженных страниц.

Системный промпт, модели и размерность, порог поиска и число технических попыток доступны
в дополнительных настройках. Неподдерживаемые temperature/max_tokens/seed не предлагаются
как работающие параметры. Для смены базовой конфигурации ручные переопределения очищаются,
чтобы значения предыдущей базы не подменяли выбранную конфигурацию.

## Предпросмотр

Предпросмотр использует тот же resolver и проверку настроек, что создание запуска.
Он читает сохранённый состав документов и параметры индексации, сравнивает отпечатки
с IndexVersion и не создаёт записи, коллекции или запросы к AI.
Состояние «индекс готов» берётся из БД; доступность и размерность коллекции Qdrant
проверяются worker при выполнении.

Результат предпросмотра содержит контрольную сумму плана. Интерфейс передаёт её при создании:
если настройки проекта изменились между проверкой и созданием запуска, backend возвращает
409 и предлагает перепроверить варианты. Изменение формы очищает предпросмотр.
Сохранённые конфигурации копируются как база; новые документы могут потребовать нового
индекса и новой версии конфигурации. Ключи провайдеров берутся из проекта при выполнении.

Новые API относительно базового пути `/api/v1/public/provider/projects/{project_id}/batches`:

| Метод | Путь | Данные |
| --- | --- | --- |
| POST | `/preview` | План, различия, общие индексы и `preview_sha256` |
| GET | `/configurations?offset=0&limit=50` | Сохранённые конфигурации пакетных запусков |
| GET | `/{id}/results?variant_id=...&status=...` | Результаты с эталонами, фильтрами и пагинацией |
| GET | `/{id}/export?format=json` | Полная выгрузка |
| GET | `/{id}/export?format=csv` | Табличная выгрузка |

Вариант запроса создания/предпросмотра может содержать `configuration_version_id` и
ручные `settings`. Оба источника проверяются в пределах проекта. `preview_sha256`
необязателен для совместимости существующих API-клиентов, интерфейс всегда его передаёт.
Миграции БД для этого этапа не нужны.

## Форматы экспорта

JSON (`schema_version=1`) содержит:

- дату экспорта, `is_partial` и явное `metrics: {status: "not_implemented", scores: null}`;
- запуск, отобранные вопросы, прогон, варианты, статусы, политику очереди и применённые настройки;
- версию набора, её SHA-256, выбранные примеры с эталонами/подтверждениями и состав документов;
- версии конфигураций и индексов с отпечатками, параметрами и контрольными суммами документов;
- все результаты, задания и технические попытки: вопрос, найденные фрагменты с порядком и
  оценками, фактический контекст, системный промпт, история/сообщения, ответ, времена,
  расход токенов и ошибки из полной трассы.

CSV использует UTF-8 с BOM. На каждую техническую попытку формируется строка; ожидающий
или не начавшийся результат тоже получает строку. В первых столбцах — вопрос, эталон,
ответ, контекст и статус; полные трассы и настройки сохранены JSON-значениями в отдельных
столбцах. Пустой расход не заменяется нулём. Ячейки, похожие на формулы электронных таблиц,
экранируются; JSON сохраняет исходный текст.

Экспорт выполняется потоком и не ограничивается страницей в 25/100 результатов.
В PostgreSQL используется отдельная транзакция REPEATABLE READ с READ ONLY: состояния
внутри одного файла согласованы, даже если worker продолжает обработку.
Незавершённый/отменённый запуск отмечается `is_partial=true`. API-ключи не входят в выгрузку;
дополнительно применяется удаление известных credentials из вложенных данных.

## Проверки

`backend/tests/test_metrics_analysis.py`: отсутствие побочных действий предпросмотра,
совместимость/разделение индексов, обнаружение устаревшего плана, повторное использование
сохранённых настроек, привязка эталона к версии, фильтры, полная выгрузка за пределами страницы,
ошибки/повторы, неизвестные токены, частичный экспорт, безопасный CSV и область проекта.

`batches.component.spec.ts` создаёт настоящий Angular-компонент с его шаблоном в jsdom:
проверяются предупреждение о недоступных метриках, три колонки результата, таблица различий,
необходимость индекса, смена конфигурации, сброс устаревшего предпросмотра, запуск очереди
и скачивание файла. Production-сборка проверяет строгие Angular-шаблоны.

Для ручной проверки внешнего вида откройте проект с контрольным документом, выберите
проверенный набор, сравните top_k=3/5 и вариант с другим chunk_size, запустите сбор и
откройте результат. Убедитесь, что ответ и контекст содержат «КЕДР-7429», эталон виден рядом,
а JSON/CSV скачиваются. Подключение вашего LLM проверяется в развёрнутом окружении.

Формат подключения оценщиков, тестовая заглушка и независимая история проверок:
[контракт метрик](metric-contracts.md).

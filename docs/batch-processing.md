# Пакетная обработка вопросов

Вкладка проекта **«Анализ метрик»** позволяет выбрать набор и его версию, раздел
`tuning` или `test`, задать несколько вариантов настроек и число независимых прогонов.
Все выбранные вопросы должны быть проверены человеком. Настройки, оставленные пустыми,
берутся из проекта при создании пакета. После создания можно проверить применённые настройки,
затем нажать «Продолжить в фоне».

## Одинаковые правила RAG

Обычный чат и пакет используют `backend/core/rag.py:execute_rag`: подготовку индекса,
эмбеддинг вопроса, поиск, ограничение контекста, генерацию и сохранение полной трассы.
Пакетные вопросы всегда независимы: история пуста, session_id нельзя задать, ответы
не добавляются в обычную историю чата. Эталонные ответы и подтверждения не передаются LLM.

Отсутствие контекста (`no_context`) отличается от ошибки поиска. При отказе retrieval
LLM не вызывается, результат получает `error` и не увеличивает счётчик успешных ответов.
Ошибки retrieval и генерации одного вопроса не останавливают остальные вопросы.

## Что фиксируется

- `BatchRun`: проект, неизменяемая версия набора, выбранные ID вопросов и split,
  число прогонов, политика независимой истории и ссылка на исходный повторяемый пакет.
- `BatchVariant`: порядок и имя варианта, неизменяемые настройки проекта без ключей,
  `ConfigurationVersion`, `IndexVersion` и фактически применённые настройки.
- `BatchQuestionResult`: вариант, ID вопроса, номер независимого прогона и статус.
- `BatchResultAttempt`: отдельная техническая попытка результата, её номер, тип
  (`initial` / `technical_retry`) и ссылка на `ExecutionRun` с полной трассой ответа.

Цепочка результата: результат → вариант → пакет → версия набора; попытка → ExecutionRun
→ версии конфигурации/индекса → документы и их контрольные суммы.
API результатов возвращает также ID версии набора, конфигурации и индекса каждой попытки.
Содержимое вопроса, найденные фрагменты, контекст, сообщения модели, ответ, времена,
неизвестный/известный расход токенов и ошибки хранятся в `response_trace`.

Версия конфигурации не включает идентификатор оцениваемого вопроса: одинаковые настройки
используют одну конфигурацию для разных вопросов. Связь вопроса с версией набора хранится
отдельно в ExecutionRun. Существующие завершённые запуски не переписываются.

Индексы строятся по документам **выбранной версии набора**, включая старые версии документов.
Изменение текущих файлов проекта не подменяет корпус подготовленного пакета.
Варианты чанкинга разделяют коллекции; изменение только top_k, лимита контекста,
порога поиска или параметров генерации переиспользует совместимый индекс.

Ключи API берутся из проекта только при выполнении и в снимки не входят.
URL провайдеров фиксируются при создании. Снимок с credentials в URL или текстовых
настройках отклоняется: секреты следует задавать в полях API-ключей проекта.
Смена ключей не требует нового индекса, но влияет на доступность провайдера.

## Прогон и технический повтор

1. `repeats` создаёт независимые результаты для каждого вопроса и варианта с номерами
   `repeat_number` от 1. Это экспериментальные повторы, даже если ответы одинаковы.
2. `max_attempts` (1–3, по умолчанию 1) повторяет временный сбой отдельного этапа внутри
   одного ExecutionRun. Все попытки этапа остаются в `response_trace.attempts`.
3. «Повторить после ошибки» создаёт новый ExecutionRun для того же результата,
   с `kind=technical_retry`. Исходная ошибочная попытка сохраняется, новый прогон не создаётся.
4. «Создать повторный прогон» создаёт новый пакет с `rerun_of_id`, теми же зафиксированными
   версиями и настройками. Старые результаты остаются неизменными. Новый пакет выполняется отдельно.

Повторный вызов выполнения обрабатывает только `pending`; успешные и ошибочные результаты
не выполняются заново автоматически. Это позволяет продолжать пакет без дублирования ответов.
Технический повтор успешного результата запрещён.

## API

Базовый путь: `/api/v1/public/provider/projects/{project_id}/batches`.

```json
{
  "name": "Контроль RAG",
  "question_set_version_id": "UUID проверенной версии",
  "split": "test",
  "repeats": 2,
  "variants": [
    {"name": "3 фрагмента", "settings": {"top_k": 3, "max_context_chars": 2000}},
    {"name": "5 фрагментов", "settings": {"top_k": 5, "max_context_chars": 4000}}
  ]
}
```

`POST` создаёт пакет, но не начинает обращения к AI. Необязательный `example_ids`
ограничивает выбор вопросами из выбранного split. Неизвестные, неподдерживаемые параметры,
повторяющиеся ID, смешение tuning/test и непроверенные вопросы отклоняются до выполнения.
Допустимые настройки варианта: `top_k`, `max_context_chars`, `score_threshold`,
`max_attempts`, `chunk_size`, `chunk_overlap`, `embedding_model`, `embedding_dimension`,
`llm_model`, `system_prompt`. Модель и размерность эмбеддингов задавайте согласованно.
Проверяются диапазоны и `chunk_overlap < chunk_size`.

| Метод и путь | Назначение |
| --- | --- |
| `POST /` | Создать пакет и зафиксировать варианты |
| `GET /?offset=0&limit=25` | Список пакетов и счётчики |
| `GET /{batch_id}` | Версии и настройки вариантов |
| `POST /{batch_id}/execute` | Выполнить ожидающие результаты |
| `GET /{batch_id}/results?offset=0&limit=25` | Результаты со всеми техническими попытками и трассами |
| `POST /{batch_id}/results/{result_id}/retry` | Повторить результат после ошибки |
| `POST /{batch_id}/rerun` | Создать новый пакет с теми же условиями |

Для создания/списка используется базовый путь без завершающего `/`.
Ответы списка содержат `total` и `items`; максимум страницы 100.
Ограничения: 20 вариантов, 10 прогонов, 10000 результатов на пакет.

## Выполнение и восстановление

Пакет выполняет Celery, независимо от браузера. `POST /{batch_id}/execute` и
`POST /{batch_id}/results/{result_id}/retry` возвращают **202** после сохранения
задания в БД. `POST /{batch_id}/cancel` запрашивает отмену; повторный `execute`
продолжает оставшиеся вопросы. Вкладка обновляет состояние каждые 3 секунды.

Текущий вопрос заканчивается в пределах таймаута; следующие после отмены не запускаются.
Сохранённые ответы остаются неизменными. Фоновые технические попытки ограничены,
при временном сбое сохраняются отдельные ExecutionRun с тем же repeat_number.
`background_job` в представлении попытки указывает ID задания, его политику и номер попытки.

Статусы пакета: `pending`, `queued`, `running`, `cancelling`, `cancelled`,
`completed`, `completed_with_errors`, `interrupted`. Прогресс и задания хранятся в БД,
а не в Redis-результатах. Повторные сообщения не пересоздают готовые результаты.

Инфраструктура, таймауты, восстановление и проверенные сценарии описаны в
[надёжном фоновом выполнении](background-execution.md).

## Проверка

`backend/tests/test_batches.py` использует контрольный документ и настоящий локальный
Qdrant; внешний LLM заменён проверяемым ответом. Проверяются несколько конфигураций,
разделение/переиспользование индексов, повторные прогоны, изоляция истории, сохранение версий
после изменений проекта, одинаковые сообщения чата и пакета, отказы поиска/генерации,
отсутствие контекста, попытки этапов и результата, восстановление, область проекта,
валидация настроек и миграция вверх/вниз.

Для окончательной ручной проверки на развёрнутых сервисах:

1. Загрузите `backend/tests/fixtures/rag_control.txt`, создайте вопрос о коде доступа
   (ответ «КЕДР-7429»), подтвердите пример человеком и выберите его версию.
2. Во вкладке пакетов создайте два варианта с разными top_k, выполните пакет и откройте
   подробности результата. Проверьте фрагмент, фактический контекст, ответ и ID версий.
3. Остановите Qdrant и создайте повторный прогон. Дождитесь ошибок retrieval без ответов LLM.
4. Запустите Qdrant и повторите один ошибочный результат. Проверьте, что исходная ошибка
   сохранилась как попытка 1, успешный ответ — как попытка 2, а номер прогона не изменился.

Реальные PostgreSQL, Redis, Qdrant и Celery проверены в изолированном Docker-окружении
с тестовым провайдером AI; проверка с вашим LLM и внешний вид вкладки остаются ручными.

Интерфейс проверки вариантов и экспорта: [Анализ метрик](metrics-analysis.md).

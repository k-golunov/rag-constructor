# Надёжное фоновое выполнение пакетов

## Запуск

```sh
docker compose up --build -d
```

Backend применяет миграции, включая `0009`, до начала обслуживания запросов.
Worker и планировщик ожидают healthcheck backend. Для пакетов нужны:

- `postgres`: версии, вопросы, прогресс, ExecutionRun и долговечные задания BatchJob;
- `redis`: Celery broker; AOF включён, данные сохраняются в `redisdata`;
- `batch-worker`: очередь `batches`, Linux prefork, по умолчанию 2 процесса;
- `worker`: очередь `celery`, 1 процесс, существующая обработка документов и отправка outbox;
- `scheduler`: Celery Beat каждые 5 секунд ставит задачу отправки outbox;
- общий том `uploads` для backend и обоих worker, чтобы новые индексы читали версии документов.

Оба модуля задач явно указаны в `include` Celery. Раньше обработчик документов
не регистрировался автоматически при запуске через `backend.tasks.worker`.
Celery восстанавливает соединение с Redis при старте/переподключении.
Планировщик должен работать в одном экземпляре; повторные доставки всё равно безопасны.

Без Docker, из корня репозитория в Linux, с одинаковыми переменными окружения:

```sh
celery -A backend.tasks.worker.celery_app worker -Q batches --concurrency=2 --loglevel=info
celery -A backend.tasks.worker.celery_app worker -Q celery --concurrency=1 --loglevel=info
celery -A backend.tasks.worker.celery_app beat --loglevel=info --schedule=/tmp/rag-celerybeat
```

Жёсткие лимиты времени рассчитаны на Linux prefork; для Windows используйте Docker.

## Долговечная очередь

При нажатии «Продолжить в фоне» API сначала фиксирует BatchJob в PostgreSQL и только
после коммита пытается отправить UUID в Celery. API-ключи, текст вопроса и документы
в сообщение задачи не входят. API возвращает 202, не выполняя RAG в запросе страницы.
При недоступном Redis задание остаётся `queued` с `broker_unavailable`; Beat отправит
его после восстановления подключения без повторного действия пользователя.

Одна задача обрабатывает один результат. После завершения worker в одной транзакции
фиксирует статус задания и создаёт задание следующего ожидающего вопроса.
Если worker остановится между коммитом и отправкой следующей задачи, Beat обнаружит
уже сохранённый outbox. Прогресс доступен через обычные GET пакета/результатов;
состояние Redis result backend для него не требуется.

Статусы BatchJob: `queued`, `published`, `running`, `success`, `error`, `cancelled`.
Сохраняются время доступности, отправки, начала/окончания, срок аренды доставки,
число начатых технических попыток, код ошибки и снимок действовавшей политики.
`GET /batches/{id}` возвращает `job` с текущим заданием и лимитами.

## Ограничения и повторные попытки

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `BATCH_QUESTION_TIMEOUT_SECONDS` | 180 | Общий лимит вопроса, включая индекс, поиск и генерацию |
| `BATCH_JOB_MAX_ATTEMPTS` | 3 | Максимум технических выполнений задания, включая первое |
| `BATCH_RETRY_DELAY_SECONDS` | 10 | Начальная задержка автоматического повтора |
| `BATCH_WORKER_CONCURRENCY` | 2 | Процессы одного batch-worker |

Политика записывается в BatchJob при создании, затем привязывается к ExecutionRun
в `details.background_job`; API попыток возвращает её рядом с полной трассой.
Независимый экспериментальный прогон по-прежнему задаётся `repeats` и создаёт отдельные
результаты. `max_attempts` варианта повторяет этап внутри ExecutionRun.
Фоновый повтор BatchJob создаёт следующий ExecutionRun для того же результата.
Таким образом, технические повторы не становятся дополнительными успешными примерами.

Повторяются временные сетевые ошибки, timeout, 429/5xx и потеря worker.
Ошибки в данных, размерности, неверных настройках или постоянный отказ провайдера
автоматически не повторяются. Между попытками — задержка с удвоением.
После исчерпания лимита вопрос остаётся ошибочным, обработка остальных продолжается.
Повтор после ошибки по явному действию пользователя создаёт новое задание с новой
ограниченной политикой, сохраняя предыдущие попытки.

`asyncio.wait_for` ограничивает асинхронное выполнение вопроса. Soft limit Celery равен
лимиту вопроса + 30 секунд, hard limit — + 60. Последний останавливает зависший процесс,
включая блокирующий код. Prefetch равен 1; каждый процесс получает одну активную задачу.
Один пакет выполняется последовательно; разные пакеты могут идти параллельно.
Масштабирование числа worker увеличивает общую параллельность.

## Отмена и продолжение

`POST /batches/{id}/cancel` возвращает 202. Если задача ещё не выполняется, она получает
`cancelled`; сообщение в Redis при доставке игнорируется. Если вопрос уже выполняется,
пакет получает `cancelling`: текущая попытка завершится в пределах лимита, ответ сохранится,
следующий вопрос не начнётся. После этого статус пакета — `cancelled`.

Повторный `POST /batches/{id}/execute` очищает признак отмены и ставит оставшуюся работу
в очередь. Успешные ответы пропускаются. Отменённая техническая попытка в ожидании
повтора может быть продолжена; постоянные ошибки требуют отдельной команды retry.
При попытке продолжить ещё выполняющуюся отмену API возвращает 409.

Вкладка автоматически обновляет прогресс, показывает отмену, ошибки брокера и политику
текущего задания. Её закрытие не отменяет работу; при повторном открытии сведения берутся из БД.

## Перезапуск и повторная доставка

- `acks_late` и `reject_on_worker_lost` разрешают повторную доставку после потери процесса.
- Session advisory lock PostgreSQL удерживается на весь результат через промежуточные
  коммиты. Вторая доставка не может параллельно выполнять тот же пакет.
- При старте задачи повторно проверяются BatchJob, active_job_id и конечный статус результата.
  Задание уже завершённого результата не обращается к LLM повторно.
- Если процесс погиб до сохранения конечного статуса, незавершённый ExecutionRun получает
  `execution_interrupted`; новая попытка сохраняется отдельно. Готовые результаты сохраняются.
- Если готовый ответ уже сохранён, но статус результата/задачи ещё не зафиксирован,
  он восстанавливается из ExecutionRun без повторной генерации.
- Истёкшая доставка возвращается через outbox после hard limit + 30 секунд, даже если
  сообщение/подтверждение потеряно. Активный worker дополнительно защищён advisory lock.
- Уникальные ограничения `(variant, example, repeat)` и `(result, attempt number)`
  не позволяют создавать дубли логического результата.

Гарантия относится к сохранённым результатам. Если процесс погиб после запроса к внешнему
LLM, но до сохранения ответа, может понадобиться повторное обращение к провайдеру.
Без поддержки idempotency у провайдера гарантировать единственный оплачиваемый запрос нельзя.

## Проверено 25 октября 2026

Автотесты: очередь до обращения к broker, повторный submit, потеря подтверждения отправки,
ограничение попыток, timeout, отмена до/во время вопроса и в ожидании повтора, продолжение,
потеря worker, восстановление после сохранения ответа, повторная доставка, регистрация
Celery, сохранение политики, миграция 0009 вверх/вниз.

Отдельно проверены настоящие PostgreSQL 15, Redis, Qdrant и Linux Celery prefork в
изолированных Docker-контейнерах. Вместо платного AI использован OpenAI-совместимый
контрольный HTTP-сервис:

1. Загружен контрольный документ, проверены 3 вопроса и создан пакет.
2. После первого сохранённого ответа worker принудительно остановлен сигналом KILL и запущен
   снова. Все 3 результата завершились; число попыток: `[1, 2, 1]`. Первый ответ не пересоздавался.
3. Повторно доставлена завершённая Celery-задача: число обращений к модели не увеличилось.
4. Redis остановлен перед постановкой следующего пакета. API сохранил задание с
   `broker_unavailable`. После запуска Redis пакет завершился без повторного submit.
5. Выполнение отменено во время вопроса: 1 ответ сохранён, 2 вопроса остались ожидающими.
   После продолжения — 3 успешных ответа, каждый с одной попыткой.

Временные контейнеры и тестовые данные удалены после проверки. Данные существующих
проектов не использовались. Внешний вид вкладки и взаимодействие с вашим настоящим
LLM можно проверить вручную по [контрольному сценарию](batch-processing.md#проверка).

# Наборы вопросов для анализа метрик

## Что реализовано

- Ручное создание, редактирование, исключение примеров и импорт JSON/JSONL/CSV.
- Вопрос, необязательный эталон, подтверждающие выдержки, категория, отсутствие
  ответа в документах, статус проверки человеком и назначение `tuning`/`test`.
- Подтверждения ссылаются на неизменяемые версии исходных документов, а не чанки.
- Все изменения, включая проверку, создают новую неизменяемую версию набора.
- Запуск закрепляется за версией набора и конкретным проверенным примером.
- Старые версии и снимки завершённых запусков не меняются при редактировании.

## Открытие наборов

Откройте вкладку **Наборы вопросов** в проекте. Список загружается автоматически;
при необходимости нажмите **Обновить список наборов**. Отдельные пароли,
переменные окружения и заголовки авторизации для наборов не требуются.

Эталоны и подтверждения сохраняются во внутреннем снимке
запуска и не добавляются в промпт LLM. Наборные RAG-вопросы выполняются отдельно,
без диалоговой истории, и не копируются в обычную публичную историю чата.
Ответ API содержит идентификаторы версии и раздела, но не эталон из библиотеки.

## Работа через интерфейс

1. Загрузите исходные документы: они должны получить `document_version_id`.
2. Откройте наборы, создайте набор и добавьте вопросы вручную либо импортируйте
   файл. Каждый новый пример получает статус **Не проверен**.
3. При необходимости добавьте эталон, категорию, отметку отсутствия ответа.
   Выберите **Подбор настроек** или **Итоговая проверка**.
4. Выберите исходный документ и вставьте точную подтверждающую выдержку.
   Если она встречается несколько раз, укажите начальную позицию.
5. После фактической проверки введите имя проверяющего и нажмите
   **Подтвердить проверку**. Для ошибки есть **Требует исправления**.
6. Выберите версию и выполните проверенный вопрос. Измените параметры проекта
   и выполните его повторно из той же версии набора.

Имя проверяющего и серверное время фиксируют явное действие оператора.
Приложение не проверяет личность человека и не утверждает, что статус сам
доказывает правильность эталона. Автоматической генерации и проверки вопросов нет.

В исторической версии редактирование отключено, но просмотр, экспорт и
запуски проверенных примеров доступны. Изменение вопроса, эталона, выдержек,
категории или назначения снимает проверку только у изменённого примера в новой
версии. Остальные неизменённые проверенные примеры сохраняют статус.

## Независимость от чанкинга

У набора закреплён полный состав исходных документов и его SHA-256.
Каждая выдержка хранит:

- `document_version_id`, исходное имя и SHA-256 исходного файла;
- точный текст `quote`;
- позиции `start_char` и `end_char` в полном извлечённом тексте;
- SHA-256 извлечённого текста и имя парсера.

Позиции нумеруются с нуля в Unicode-символах Python; `end_char` не включается.
Они относятся к тексту парсера, а не байтам файла и не тексту отдельного чанка.
При сохранении проверяются контрольная сумма файла и точное совпадение цитаты.
Неоднозначные цитаты без позиции, выход за границы и ссылки на документы
другого проекта отклоняются. Смена чанкинга не меняет эти подтверждения.

Смена состава или версии документа требует новой версии набора и проверки.
Запуск RAG со старым набором на другом корпусе возвращает 409 до обращения
к модели. Кнопка **Обновить состав документов** создаёт новую версию с текущим
корпусом, сбрасывает проверку и удаляет подтверждения только из новой версии.
Прежние версии и их подтверждения остаются доступны.

## Импорт и экспорт

Принимаются UTF-8 и UTF-8 BOM, до 10 МБ и до 10000 примеров на набор.
Импорт добавляет вопросы в новую версию существующего набора атомарно:
ошибка хотя бы в одной строке не сохраняет частичный результат.

Пример файла: `backend/tests/fixtures/questions-example.json`. Он предназначен
для контрольного документа `rag_control.txt`; примеры остаются непроверенными,
а подтверждающие выдержки нужно добавить вручную.

JSON — массив примеров либо объект `{"schema_version": 1, "examples": [...]}`.
JSONL — один объект примера на строку. CSV использует столбцы:

```text
id,question,reference_answer,evidence,category,unanswerable,split
```

Обязателен только `question`. `id` можно не задавать; UUID создаётся сервером.
`evidence` в CSV — строка с JSON-массивом подтверждений, с обычным CSV-экранированием.
`unanswerable` принимает `true/false` или `1/0`; назначение по умолчанию — `tuning`.
Пустой эталон означает неизвестный ответ, а не неправильный ответ.

Статус проверки не принимается из импорта или обычного редактирования.
Экспорт содержит вопросы и подтверждения без статуса проверки; повторный импорт
не переносит утверждение о человеческой проверке. Для повторного анализа уже
проверенного набора используйте существующую версию, не экспорт/импорт.

Повторяющиеся идентификаторы и вопросы, в том числе между `tuning` и `test`,
отклоняются. Регистр и повторные пробелы при проверке дубликатов игнорируются.
Используйте `tuning` для подбора, затем фиксируйте настройки перед `test`.
Сами метки не мешают человеку вручную использовать итоговые вопросы для подбора.

## API

Методы доступны без дополнительных паролей и заголовков:

```text
POST   /api/v1/public/provider/projects/{project_id}/question-sets
GET    /api/v1/public/provider/projects/{project_id}/question-sets
GET    .../question-sets/{set_id}/versions
GET    .../question-sets/{set_id}/versions/{version_id}
GET    .../question-sets/{set_id}/versions/{version_id}/export
POST   .../question-sets/{set_id}/examples
PATCH  .../question-sets/{set_id}/examples/{example_id}
DELETE .../question-sets/{set_id}/examples/{example_id}?base_version_id=...
POST   .../question-sets/{set_id}/examples/{example_id}/review
POST   .../question-sets/{set_id}/import?base_version_id=...
POST   .../question-sets/{set_id}/versions
```

Изменения передают `base_version_id`. Если за это время появилась новая
версия, API возвращает 409 вместо потери чужих изменений. Для полного замещения
передайте список `examples` в `/versions`; `refresh_documents: true` фиксирует
новый корпус и сбрасывает проверку всех примеров этой новой версии.

Чтение версии поддерживает фильтры `?split=test&review_status=approved`.
SHA-256 ответа относится к полной версии, а поле `selection` указывает
фильтр выбранного поднабора.

Пример запуска проверенного вопроса через `/chat`:

```json
{
  "question": "Какой код доступа к архиву проекта Север?",
  "question_set_version_id": "<UUID версии набора>",
  "question_example_id": "<UUID примера>"
}
```

Вопрос должен совпадать с зафиксированным примером. Непроверенные и отклонённые
примеры не допускаются к такому запуску. Оба идентификатора обязательны вместе.
Для `/chat/generate` используются те же идентификаторы и поле `query`.

`execution_runs` содержит ссылки на версию и пример. Во внутреннем
`details.question_example_snapshot` фиксируются вопрос, эталон, подтверждения,
категория, отсутствие ответа, раздел и проверка. Редактирование набора не меняет
этот снимок. Служебные credentials в наборе отклоняются до сохранения.

## Применение и проверки

Добавлена миграция `0007`. Она создаёт `question_sets`, `question_set_versions`
и связи с запусками. Старые запуски сохраняют `null` в новых полях.
При старте backend проверьте успешное применение миграции.

152 backend-теста прошли, включая 29 проверок наборов. Проверены три формата
импорта, атомарность, цитаты и координаты, человеческая проверка, разделы,
неизменяемость, повторное использование, работа без паролей, отсутствие эталона
в запросе LLM и отказ при несовпадающем корпусе. Angular-шаблоны компилируются.

SQL миграции PostgreSQL и создание/откат схемы со связью на SQLite проверены.
Визуальная проверка новой вкладки и полный прогон с рабочими PostgreSQL,
Qdrant и реальными моделями остаются ручными: используйте сценарий выше.

# Контракт подключения будущих метрик

Текущий этап завершает сбор и передачу воспроизводимых исходных данных.
**Численные метрики, их интерпретация и LLM-оценщики пока не реализованы.**
Доступна только тестовая заглушка `transport_stub@1.0.0`: она проверяет требования
к данным и возвращает `status=validated`, `value=null`. Это не оценка качества.

## Два независимых процесса

1. **Получение ответов**: набор → варианты → Celery → индекс/поиск → LLM → ExecutionRun.
   Здесь сохраняются версии, фактический контекст, ответ, полная трасса и технические попытки.
2. **Последующая проверка/оценка**: сохранённая попытка → MetricInput → оценщик → MetricResult.
   Здесь нет вызова RAG, Qdrant, построения индекса или повторной генерации.

Модуль `core/metric_inputs.py` читает только БД. Чистый интерфейс оценщика расположен
в `core/evaluators.py` и зависит от контрактов Pydantic, а не от сервисов генерации.
Автоматической оценки после сбора ответов нет. Будущий дорогой оценщик следует запускать
отдельной задачей, передавая идентификатор/снимок сохранённого входа; очередь сбора ответов
повторно запускать не требуется.

В интерфейсе «Анализ метрик» у сохранённого ответа есть кнопка **«Проверить формат для
будущих метрик»**. Она вызывает заглушку и показывает объяснение, пропущенные данные,
версию и параметры. Предупреждение о неподключённых метриках остаётся видимым.

## MetricInput, версия 1

Авторитетная схема: `backend/db/metric_schemas.py`, класс `MetricInput`.
Схемы также доступны в OpenAPI и через `GET /metric-contracts` проекта.
Неизвестные поля не принимаются.

| Поле | Смысл |
| --- | --- |
| `schema_version` | Версия контракта, сейчас 1 |
| `question` | Вопрос сохранённой попытки |
| `answer` | Сохранённый ответ либо null, если неизвестен |
| `context` | Точный контекст, фактически переданный модели; не собирается заново из фрагментов |
| `reference_answer` | Необязательный эталон из зафиксированной версии набора |
| `evidence` | Необязательные подтверждающие выдержки с версиями документов и позициями |
| `retrieved_chunks` | Найденные фрагменты с порядком, исходными оценками и ссылками на версии документов |
| `context_chunk_ids` | Идентификаторы фрагментов, включённых в фактический контекст |
| `unanswerable`, `category` | Разметка исходного примера |
| `processing_status` | pending/running/success/error у выбранной попытки |
| `retrieval_status` | not_started/success/no_context/error |
| `provenance` | Происхождение, версии и контрольные суммы |
| `integrity_errors` | Обнаруженные несоответствия между вопросом, попыткой и версиями |
| `redaction_applied` | Признак удаления credentials из передаваемых данных |

**Пустое и неизвестное различаются.** `context=""` — известный пустой контекст после
успешного поиска без результатов; `context=null` — фактический контекст неизвестен.
`reference_answer=null` — эталон не задан. `evidence=[]` — подтверждений нет,
`evidence=null` — сведения о них отсутствуют. Неизвестные данные не заменяются нулём.
Поле `unanswerable=true` — разметка человека, а не автоматически рассчитанная оценка.

Подтверждения содержат `document_version_id`, SHA-256 исходного файла, имя файла,
`quote`, позиции `start_char/end_char` в разобранном тексте, SHA-256 этого текста
и имя парсера. Они не привязаны к chunk ID и сохраняют смысл при другой разбивке.

В provenance входят ID проекта, пакета, варианта, результата, примера, независимого
прогона и ExecutionRun, версии/хеши конфигурации, индекса и набора, контрольная сумма
состава документов и сохранённой трассы. `question_isolated` подтверждает пустую историю
в пакетном выполнении; неизвестная история не считается подтверждённой изоляцией.

По умолчанию выбирается последняя техническая попытка результата. Параметр
`execution_run_id` позволяет явно выбрать более раннюю сохранённую попытку этого
же результата. Чужую попытку или другой проект выбрать нельзя. Это не дополнительный
прогон: источником остаётся существующий ExecutionRun.

## Требования оценщика

`EvaluatorDescriptor` фиксирует:

- `id` и `version`: точную идентичность реализации;
- заголовок, описание и вид `metric` / `transport_validation`;
- поддерживаемые версии входного контракта;
- список `requirements`;
- JSON Schema параметров, совпадающую с `parameters_model` оценщика.

Каждое требование содержит `field`, `condition` и человекочитаемое объяснение.
Допустимые поля: question, answer, context, reference_answer, evidence, retrieved_chunks.
`present` требует значения, отличного от null; известные пустая строка/список допустимы.
`non_empty` дополнительно требует непустой текст или список.

Примеры **будущих**, не подключённых сейчас требований:

| Тип будущей проверки | Пример обязательных данных |
| --- | --- |
| Сопоставление с эталоном | question, answer, reference_answer: non_empty |
| Проверка опоры на контекст | answer, context: non_empty |
| Проверка подтверждений | question, answer, evidence: non_empty |

Заглушке нужны непустые question/answer и context:present. Поэтому отсутствие эталона
не мешает проверить транспорт, а известный пустой контекст допустим.

Сначала проверяются успешность источника, связи версий, изоляция вопроса, доступность
трассы и требования. Недостающие данные дают **skipped**, оценщик не вызывается.
Несовпадение вопроса, индекса, конфигурации или состава документов тоже блокирует вызов.
Исторический ответ без полной трассы не считается готовым; поиск/генерация для него
автоматически не выполняются.

## MetricResult, версия 1

```json
{
  "schema_version": 1,
  "input_sha256": "SHA-256 канонического MetricInput",
  "status": "validated",
  "value": null,
  "explanation": "Данные переданы в тестовую заглушку. Расчёт качества не выполнялся.",
  "reason_code": null,
  "missing_data": [],
  "details": {},
  "evaluator": {
    "id": "transport_stub",
    "version": "1.0.0",
    "kind": "transport_validation",
    "parameters": {}
  }
}
```

Возможные статусы:

| Статус | Значение |
| --- | --- |
| `validated` | Проверка передачи выполнена; value=null, не оценка качества |
| `skipped` | Нет успешного ответа/обязательных данных или нарушена целостность; value=null |
| `error` | Ошибка оценщика либо некорректный результат его работы; value=null |
| `scored` | Зарезервирован для следующего этапа: конечное численное значение обязательно |

NaN, бесконечность и boolean вместо числа не принимаются. Настоящий численный ноль
допустим только для будущего `scored`; пропуск/ошибка не превращаются в 0.
Транспортному оценщику запрещено возвращать scored. Никаких итоговых средних и трактовки
«хорошо/плохо» сейчас нет.

Идентичность оценщика, разрешённые параметры с применёнными значениями по умолчанию
и входной SHA фиксирует общий runner, а не произвольный код оценщика.
Он передаёт оценщику отдельную копию входа; изменение этой копии обнаруживается как ошибка.
Необработанное исключение оценщика превращается в error без изменения исходного ответа.

Интерфейс будущего модуля:

```python
class Evaluator(Protocol):
    descriptor: EvaluatorDescriptor
    parameters_model: type[BaseModel]

    async def evaluate(self, sample: MetricInput, parameters: BaseModel) -> Assessment:
        ...
```

Общий вызов: `await evaluate_saved_input(sample, evaluator, parameters)`.
Новая реализация добавляется явной регистрацией пары `(id, version)` в REGISTRY.
Сейчас там только заглушка. Запрос не может загрузить Python-модуль, URL или неизвестную
версию оценщика. Секреты будущего сервиса должны передаваться через его runtime-настройки,
а не входной контракт, параметры или сохранённое описание.

## Отдельное хранение и API

Миграция `0010` создаёт `evaluation_checks`. Запись содержит ID результата/попытки,
неизменяемый входной снимок и его SHA, снимок описания оценщика и полный MetricResult.
Новая проверка создаёт новую запись; прежняя не переписывается. Последующая техническая
попытка генерации не меняет исходный снимок проверки.

Сбой оценщика не меняет ExecutionRun и статус BatchQuestionResult. Изменение проекта,
разметки или текущего индекса не подменяет версии уже сохранённого входа.
Credentials не допускаются в сохраняемых параметрах и результатах; входные данные
дополнительно проходят удаление известных секретов.

Базовый путь: `/api/v1/public/provider/projects/{project_id}`.

| Метод и путь | Назначение |
| --- | --- |
| `GET /metric-evaluators` | Подключённые реализации, версии и требования |
| `GET /metric-contracts` | JSON Schema входа и результата |
| `GET /batches/{bid}/results/{rid}/metric-input` | Нормализованный сохранённый вход и SHA |
| `POST /batches/{bid}/results/{rid}/evaluation-checks` | Вызов заглушки и независимая запись проверки |
| `GET /batches/{bid}/results/{rid}/evaluation-checks` | История проверок с offset/limit |

Тело POST можно оставить `{}`: используются transport_stub/1.0.0 и параметры `{}`.
Необязательный execution_run_id выбирает сохранённую попытку. Неизвестные оценщики,
версии и параметры отклоняются. На read/POST действует та же область проекта и пакета,
что у исходного результата.

## Передача выгрузки без БД и генерации

JSON/CSV экспорта теперь включают `metric_input`, `metric_input_sha256` и
`evaluation_checks` каждого результата. Схема основного экспорта остаётся версией 1
с дополнительными полями; метаданные указывают версии контракта. Полные сырые трассы
всех технических попыток также сохраняются. `metrics.scores` остаётся null.

Пример использования JSON-выгрузки отдельным модулем:

```python
import asyncio
import json
from pathlib import Path
from backend.db.metric_schemas import MetricInput
from backend.core.evaluators import REGISTRY, checksum, evaluate_saved_input

async def main():
    data = json.loads(Path("answers.json").read_text(encoding="utf-8"))
    stub = REGISTRY[("transport_stub", "1.0.0")]
    for row in data["results"]:
        sample = MetricInput.model_validate(row["metric_input"])
        assert checksum(sample.model_dump(mode="json")) == row["metric_input_sha256"]
        check = await evaluate_saved_input(sample, stub, {})
        print(check.model_dump_json())

asyncio.run(main())
```

Для этого пути не нужны PostgreSQL, Redis, Qdrant и LLM. Контрольная сумма — SHA-256
UTF-8 JSON с sort_keys=True, ensure_ascii=False, separators=(",", ":"), allow_nan=False.
Полный снимок сохраняется: повторная генерация ответа ради новой метрики не требуется.

## Проверенная основа

- Автотесты подтверждают изоляцию истории, разделение/переиспользование индексов,
  версии наборов/конфигураций, восстановление Celery и защиту от повторной доставки.
- `test_metric_contracts.py` проверяет контракт и требования, пустое/неизвестное,
  заглушку без поиска/LLM, ошибки и параметры оценщика, целостность/область проекта,
  неизменяемость записей, выбор технической попытки, JSON/CSV и миграцию вверх/вниз.
- Новый DOM-тест подтверждает вызов проверки сохранённой попытки из интерфейса,
  без повторного запуска сбора и без численного значения качества.
- На настоящем PostgreSQL 15 отдельно проверены миграции до 0010 и откат/повторное
  применение 0010, передача заранее сохранённого ответа в заглушку, JSON/CSV в режиме
  REPEATABLE READ, неизменность числа ExecutionRun и удаление проекта со связанными запусками.
  Qdrant/Redis/LLM в этом тесте отсутствовали. Временная БД удалена после проверки.
- При этой проверке исправлен порядок удаления пакетов перед индексами/конфигурациями:
  прежний каскад удаления проекта нарушал внешние ключи PostgreSQL.

Реальный перезапуск worker и отключение Redis ранее проверены по сценарию
[фонового выполнения](background-execution.md). Для ручной проверки откройте сохранённый
ответ, нажмите кнопку проверки формата, убедитесь в `validated/value=null`, выгрузите JSON
и проверьте наличие metric_input, версии оценщика и отдельной записи проверки.

Следующий этап может реализовать сами показатели, LLM-оценщиков и их интерпретацию,
используя эти сохранённые входы. В текущем этапе они не включены.

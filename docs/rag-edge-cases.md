# Набор сложных случаев RAG

Синтетический корпус вымышленной компании «Северный Ветер», 72 вопроса к нему,
разбитые по типам ошибок RAG, и 20 подготовленных ответов для проверки оценщиков.

Файлы лежат в `backend/datasets/rag_edge_cases/`:

| Файл | Что внутри |
| --- | --- |
| `corpus/*.txt` | 18 документов: регламенты, старая редакция положения об отпусках, пары похожих тарифов и складов, шесть шумовых текстов |
| `questions.json` | 72 вопроса в формате импорта наборов: эталоны, точные выдержки, пояснения, стабильные `id` |
| `evaluator_fixtures.json` | 20 заранее подготовленных ответов для проверки оценщиков, помечены как тестовые |

## Категории

| Категория | Вопросов | Ловушка |
| --- | --- | --- |
| Перефразирование | 12 | Вопрос и эталон сказаны другими словами, чем документ. Ломаются поиск по совпадению слов и буквальное сравнение с эталоном |
| Похожие документы | 12 | Рядом редакция 2023 года, второй тариф или второй склад: те же фразы, другие числа |
| Несколько выдержек | 12 | Ответ собирается из двух-трёх выдержек, иногда из разных документов, иногда с подсчётом |
| Отвлекающий текст | 12 | Много текста на ту же тему без ответа, часто с тем же числом в другом смысле |
| Ошибочная предпосылка | 12 | Вопрос исходит из неверного факта. Хороший ответ его поправляет со ссылкой на документ |
| Нет ответа | 12 | Тема близка к корпусу, факта нет. Эталон пустой, `unanswerable: true`, выдержек нет |

В каждой категории 4 вопроса отмечены как `tuning`, остальные 8 — как `test`.
Пояснение из поля `explanation` видно во вкладке наборов, в карточке результата
анализа метрик и в выгрузках JSON и CSV. Модели оно не передаётся, как и эталон.

Каждая выдержка встречается в своём документе один раз, поэтому позиции сервер
находит сам. Несколько выдержек из положения 2025 года дословно повторяются в редакции
2023 года (например, про 28 дней основного отпуска). Если поиск вернул такой фрагмент
из старой редакции, ответ всё равно верен: попадание в выдержку для этих вопросов
надо считать по тексту, без сравнения `document_version_id`.

## Настройки, при которых ловушки срабатывают

Почти все документы короче 1000 символов. С размером чанка по умолчанию (800) тариф
или склад попадает в один чанк вместе с заголовком, и вопросы про «название только
в заголовке» становятся простыми. Для проверки поиска берите `chunk_size` 150–250,
`chunk_overlap` 0–30 и `top_k` 3. С большими чанками набор остаётся полезным для
проверки генерации и оценщиков.

## Как загрузить в проект

1. Создайте отдельный проект, без других документов.
2. Загрузите все файлы из `corpus/`, например одним архивом:

   ```powershell
   Compress-Archive -Path backend/datasets/rag_edge_cases/corpus/*.txt -DestinationPath "$env:TEMP\edge-cases-corpus.zip"
   ```

3. Во вкладке **Наборы вопросов** создайте набор и импортируйте `questions.json`.
4. Проверьте примеры и подтвердите проверку. После этого их можно запускать в чате
   и в пакетном сравнении вариантов.

В `questions.json` выдержки ссылаются на документ по `file_name`: идентификаторы
версий появляются только после загрузки. Сервер ищет документ в составе версии
набора по точному имени, потом по имени без каталога, если оно однозначно. Поэтому
подходит и архив, где у файлов есть папка. Если документа нет или имя совпадает
с несколькими файлами, импорт отклоняется целиком.

## Подготовленные ответы для проверки оценщиков

Ответы и контексты в `evaluator_fixtures.json` написаны вручную. Файл помечен
`"synthetic": true`, у каждого ответа есть вид:

| `kind` | Что это |
| --- | --- |
| `correct` | Правильный ответ, в том числе пересказанный своими словами |
| `incomplete` | Часть ответа пропущена, пропущенное перечислено в `missing_facts` |
| `hallucinated` | Добавлен факт, которого нет во всём корпусе (`unsupported_claims`) |
| `wrong_document` | Контекст взят из похожего, но другого документа |

Поле `expected` задаёт три признака:

- `correct` — ответ годится как итоговый;
- `grounded` — всё сказанное следует из переданного контекста, без переноса
  свойств одной сущности на другую;
- `complete` — в ответе есть всё, о чём спрашивает вопрос, а для вопросов без
  ответа есть честный отказ.

Для `wrong_document` признак `grounded` бывает разным. Если ответ дословно пересказывает
чужой фрагмент, проверка опоры на контекст его пропустит, и ошибку увидят только
сравнение с эталоном или проверка источника. Если ответ приписывает данные из чужого
фрагмента сущности из вопроса, строгая проверка опоры должна его отклонить.

Входы для оценщиков собираются без БД, Qdrant и LLM:

```python
import asyncio
from backend.core.evaluators import REGISTRY, evaluate_saved_input
from backend.datasets.edge_cases import fixture_samples

stub = REGISTRY[("transport_stub", "1.0.0")]
for fixture, sample in fixture_samples():
    result = asyncio.run(evaluate_saved_input(sample, stub, {}))
    print(fixture.id, fixture.expected, result.status)
```

`sample` — обычный `MetricInput` версии 1. `question_example_id` совпадает с `id`
вопроса в `questions.json`, остальные идентификаторы выводятся из `FIXTURE_NAMESPACE`,
поэтому такие входы не спутать с сохранёнными попытками.

## Подвыборка MIRACL-ru

В русскоязычном MIRACL есть запросы и разметка релевантных фрагментов, эталонных
ответов нет. Конвертер ничего не скачивает: ему нужны локальные файлы из репозиториев
`miracl/miracl` и `miracl/miracl-corpus` на Hugging Face — запросы в TSV, разметка
qrels в формате TREC и корпус JSONL или JSONL.GZ.

```powershell
poetry run python -m backend.datasets.miracl --topics topics.miracl-v1.0-ru-dev.tsv --qrels qrels.miracl-v1.0-ru-dev.tsv --corpus docs-0.jsonl.gz docs-1.jsonl.gz --out "$env:TEMP\miracl-ru-subset" --limit 50 --negatives 3
```

Порядок запросов задаётся хешем их идентификатора, так что повторный запуск даёт тот
же результат. Берутся запросы, у которых есть хотя бы один релевантный фрагмент и все
такие фрагменты нашлись в корпусе. К ним добавляются до `--negatives` фрагментов,
которые асессоры MIRACL разметили для этого запроса как нерелевантные. Корпус читается
потоком; в памяти остаются только фрагменты, упомянутые в qrels для подходящих запросов.

Каталог `--out` должен быть новым или пустым. В нём появятся:

- `corpus/*.txt` — по файлу на фрагмент: заголовок статьи и текст;
- `questions.json` — файл для импорта, `id` примера выводится из идентификатора запроса;
- `subset.json` — параметры отбора, контрольные суммы входных файлов и пропущенные запросы.

Эталонные ответы можно передать через `--answers`, файлом JSONL со строками
`{"query_id": "...", "answer": "..."}`. Без них `reference_answer` пустой, и пример
проверяет только поиск. Ошибки во входных файлах останавливают сборку с указанием
файла и строки.

Числа на такой подвыборке нельзя сравнивать с опубликованными результатами MIRACL.
У всех примеров категория «MIRACL-ru (адаптированная подвыборка)», и в отчётах их
нужно подписывать как результаты адаптированной подвыборки. Запросы и разметка MIRACL
распространяются по Apache 2.0, тексты фрагментов из Википедии — по CC BY-SA.
Держите результат конвертера вне репозитория.


Тесты сверяют выдержки и числа в эталонах и подготовленных ответах с корпусом,
собирают `MetricInput` и импортируют набор и подвыборку MIRACL в проект через API.

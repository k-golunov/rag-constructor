# Версии документов, конфигураций и индексов

## Реализованные гарантии

| Требование | Реализация |
| --- | --- |
| Состав и контрольные суммы файлов | SHA-256 исходных байтов, размер, имя и `document_version_id`; полный манифест в каждой версии индекса |
| Неизменяемая конфигурация запуска | `configuration_versions`: каноническая копия настроек, SHA-256 и идентификатор версии; связь с `execution_runs` |
| Происхождение индекса | Манифест документов, параметры чанкинга, эмбеддер, размерность, endpoint и версии компонентов обработки |
| Разделение несовместимых вариантов | Отдельная коллекция Qdrant для каждого отпечатка состава документов и настроек индексации |
| Повторное использование | Готовая версия используется повторно при совпадении отпечатка; смена LLM, промпта, `top_k` или лимита контекста не перестраивает индекс |

## Документы

При загрузке вычисляется SHA-256 исходных байтов файла. Сохранённые версии
находятся в `UPLOAD_DIR/{project_id}/versions/{sha256}.{extension}`.
Запись `document_versions` содержит исходное имя, размер, контрольную сумму
и путь. Файл не перезаписывается при загрузке другого содержимого с тем же именем.
Те же имя и байты в проекте повторно используют существующую версию документа.

`data_sources` представляет текущий состав документов. Повторная загрузка
имени переключает ссылку на новую версию. Удаление источника исключает его из
текущего состава через `is_active`; сохранённые версии и старые индексы остаются.
Удаление или замена документа не изменяют манифесты завершённых запусков.

Перед построением индекса проверяются размер и контрольная сумма каждого
сохранённого файла. Несовпадение приводит к ошибке; повреждённый файл не
используется для построения нового варианта.

## Индексы

Версия индекса определяется SHA-256 канонического представления двух частей:

- Отсортированный манифест: идентификаторы версий, имена, SHA-256 и размеры файлов.
- Настройки индексации: размер чанка и перекрытия, алгоритмы парсинга/разбиения,
  модель и размерность эмбеддингов, адрес провайдера, метрика Cosine и версии
  библиотек `pypdf`, `python-docx`, `langchain-text-splitters`.

Ключи API не входят в отпечаток; их ротация не требует переиндексации. Адреса
в снимках сохраняются без userinfo, query и fragment. Идентификатор удалённой
модели фиксируется как задан в настройках; неизменность весов за модельным
алиасом у внешнего провайдера приложение гарантировать не может.

Для каждого отпечатка создаётся отдельная коллекция
`rag_{project_id_without_hyphens}_{fingerprint_prefix}` и строка `index_versions`.
Она содержит полный манифест, параметры, количество фрагментов по документам,
состояние `pending`, `ready` или `failed`. Точки имеют детерминированные UUID,
связанные с индексом, документом и номером фрагмента. Метаданные точки содержат
версии документа и индекса, контрольную сумму документа и параметры разбиения.

После изменения параметров индексации следующий RAG-запрос автоматически
строит отдельный индекс из сохранённых версий файлов. Повторно загружать
уже версионированные документы не нужно. Новый вариант собирает весь текущий
корпус; экономия эмбеддингов между частично совпадающими корпусами пока не
реализована. Возврат к прежнему составу и настройкам повторно использует
готовую коллекцию без нового эмбеддинга документов.

`top_k`, порог близости, лимит контекста, LLM и системный промпт не входят
в отпечаток индекса. Эмбеддинг нового вопроса всё равно выполняется.

Приложение не дописывает документы в готовые версии индекса. При частичной
записи незавершённого индекса повторная попытка использует те же UUID точек,
поэтому не создаёт дубликаты. Ошибка нового варианта не вызывает переход к
старой коллекции. Готовая коллекция проверяется на наличие и размерность;
при недоступности Qdrant или исчезновении коллекции возвращается ошибка.

Параллельные сборки одного варианта сериализуются блокировкой строки индекса
в БД и асинхронной блокировкой внутри процесса. Реальный конкурентный прогон
с PostgreSQL и несколькими worker-процессами остаётся ручной проверкой.

## Конфигурации и запуски

При старте принятого запуска создаётся или повторно используется
`configuration_versions` с канонической копией действующих настроек.
Для RAG в неё включён снимок выбранного индекса и его манифеста.
`execution_runs.configuration_version_id` и `index_version_id` связывают
выполнение с этими версиями; для генерации по готовому контексту индекс не нужен.

Существующие ответы API дополнены `configuration_version_id`; сведения об
индексе и документах доступны в `applied_settings`. Загрузка возвращает
`document_version_id`, `index_version_id`, манифест и `index_reused`.
Новых публичных адресов чтения внутреннего журнала нет.

Проект может изменяться после старта: провайдеры и параметры запуска уже
зафиксированы. ORM отклоняет изменение сохранённых определений документов,
конфигураций и индексов. Прямые административные изменения файлов, SQL или
коллекций Qdrant вне приложения не являются поддерживаемым способом редактирования
версий. Сохраняйте резервные копии БД, файлов и Qdrant совместно.

## Обновление существующей установки

Добавлена миграция `0005` после `0004`. Она создаёт три таблицы версий и связи
с источниками и запусками. Стандартная инициализация backend применяет её
при запуске; проверьте успешное завершение миграций перед использованием.

Старые запуски и их снимки не переписываются: отсутствующие исторические
сведения не восстанавливаются предположениями. У старых источников
`document_version_id` остаётся `null`. Их необходимо загрузить заново, чтобы
вычислить достоверные контрольные суммы и построить первый версионированный
индекс. До этого RAG-запрос возвращает ошибку, а не использует старую общую
коллекцию. Старые коллекции и файлы автоматически не удаляются.

## Проверка

107 backend-тестов прошли, включая 24 проверки версионирования. Проверены
замена и повторная загрузка файлов, смена состава корпуса, разные параметры
чанкинга и эмбеддеров, возврат к старому индексу, неизменяемость снимков,
контрольные суммы, частичная запись и повтор, ZIP, Celery и устаревшая задача.
Также проверена одновременная сборка в одном процессе.

Для миграции проверены SQL PostgreSQL и создание/откат схемы со связями на
SQLite. Рабочая PostgreSQL, сервер Qdrant и реальные модели в этом прогоне
не использовались. Изолированные тесты используют настоящий локальный
движок Qdrant и подменённые внешние ответы моделей.
